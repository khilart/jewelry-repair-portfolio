# Delta: Stone Orders — заказ камней поставщику

## ADDED

### Модель: jewelry.stone.order — Заказ камней

Нумерация `GO2026-NNNN`. Наследует `mail.thread` — комментарии и история действий живут
в чаттере, а не в перезаписываемом поле.

| Поле | Тип | Описание |
|------|-----|----------|
| name | Char | `GO%(year)s-` из последовательности, readonly |
| supplier_id | Many2one res.partner | Поставщик, required, домен по `is_stone_supplier` |
| purpose | Selection | `repair` — под заказ ремонта, `stock` — на склад. Required |
| repair_order_id | Many2one jewelry.repair.order | Обязателен при `purpose = repair`, запрещён при `stock` |
| state | Selection | `draft / confirmed / in_progress / shipped / received / rejected / cancelled` |
| stones_payable | Selection | `yes` — камни оплачиваем, `no` — заказ поставщика |
| commission_pct | Float | Снимок процента комиссии на момент создания |
| supplier_waybill | Char | Номер накладной поставщика, формат любой |
| fetched_at | Datetime | «Забран поставщиком», readonly, ставится автоматически |
| last_change_at | Datetime | «Последнее изменение», readonly — watermark для опроса поставщиком |
| shipped_complete | Boolean (compute) | Полнота отгрузки, считается сопоставлением таблиц |
| request_line_ids | One2many | Таблица «Запрошено» |
| shipped_line_ids | One2many | Таблица «Отгружено» |
| notes | Text | |

### Модель: jewelry.stone.order.request.line — Строка запроса

Заполняет менеджер в черновике. Описывает **требование**, а не конкретный камень.

| Поле | Тип | Описание |
|------|-----|----------|
| order_id | Many2one | ondelete cascade |
| gem_type_id | Many2one jewelry.gem.type | Required |
| origin | Selection | `natural` / `lab_grown`. **Required** |
| cut_shape | Selection GEM_CUT_SHAPES | |
| standard_size_id | Many2one jewelry.gem.standard.size | Размер в мм |
| quantity | Integer | Required, default 1 |
| weight_ct | Float (16,4) | Вес за штуку |
| total_weight_ct | Float (compute, store) | `quantity × weight_ct` |
| certificate_ref | Char | Номер сертификата, **необязательный** |

### Модель: jewelry.stone.order.shipped.line — Строка отгрузки

Заполняет поставщик по API или менеджер руками. Описывает **факт**.

| Поле | Тип | Описание |
|------|-----|----------|
| order_id | Many2one | ondelete cascade |
| request_line_id | Many2one request.line | **Необязательная** — склад может добавить то, чего не просили |
| gem_type_id, origin, cut_shape, standard_size_id | | Чтобы строка без привязки была описуемой |
| certificate_ref | Char | Номер сертификата |
| quantity | Integer | Required, default 1 |
| weight_ct | Float (16,4) | Фактический вес за штуку |
| price_unit | Monetary | Продажная цена клиенту, от поставщика |
| subtotal | Monetary (compute, store) | `quantity × price_unit` |
| supplier_amount | Monetary (compute, store) | `subtotal × (1 − commission_pct/100)` — что отдаём поставщику |
| disposal | Selection | Пусто / `returned` / `broken` |
| broken_charge_to | Selection | `workshop` / `client` / `supplier`, только при `disposal = broken` |

### Модель: jewelry.stone.return — Возврат камней поставщику

Нумерация `GR2026-NNNN`. Состояния `draft` / `done`.

| Поле | Тип | Описание |
|------|-----|----------|
| name | Char | readonly |
| stone_order_id | Many2one jewelry.stone.order | Исходный заказ камней, required |
| supplier_id | Many2one | related от заказа |
| return_date | Date | Required |
| waybill | Char | Наш номер накладной возврата |
| line_ids | One2many jewelry.stone.return.line | `shipped_line_id`, `quantity`, `weight_ct` |

### Расширения существующих моделей

`res.partner` — `is_stone_supplier` (Boolean), `stone_commission_pct` (Float, значение по
умолчанию для новых документов).

`jewelry.repair.order` — `stone_order_ids`, `stone_order_count` (compute),
`last_stone_order_state` (compute).

`jewelry.repair.gem.line` — `stone_order_line_id` (Many2one shipped.line, readonly).
Поле живёт в модуле заказов камней: `jewelry_repair_base` о нём не знает и зависимости
не получает.

### Requirement: Сертификат всегда на один камень

Партийных сертификатов не бывает. Строка с заполненным номером сертификата обязана иметь
количество 1 — иначе двенадцать камней уедут под одним номером и разойдутся с учётом
поставщика.

#### Scenario: Сертификат с количеством больше одного отклоняется

- GIVEN строка запроса или строка отгрузки
- WHEN заполнен `certificate_ref` И `quantity > 1`
- THEN запись отклоняется с сообщением, что сертификат относится к одному камню

#### Scenario: Без сертификата количество любое

- GIVEN строка с пустым `certificate_ref`
- WHEN `quantity = 12`
- THEN запись проходит — это мелочь, она идёт партией

### Requirement: Происхождение камня обязательно

Менеджер запрашивает натуральный камень, склад не должен подставить выращенный: разница
в цене — порядок величины, ошибка дорогая в обе стороны.

#### Scenario: Строка запроса без происхождения не заводится

- GIVEN заказ камней в черновике
- WHEN менеджер пытается добавить строку запроса без `origin`
- THEN запись отклоняется

Защита стоит **на вводе, а не на подтверждении**: поле обязательное, поэтому запрос без
происхождения до подтверждения просто не доживает. Отдельная проверка в `action_confirm`
была бы недостижимым кодом.

### Requirement: Цепочка состояний

| Переход | Кто |
|---|---|
| `draft → confirmed` | менеджер |
| `confirmed → draft` | менеджер, **только пока поставщик не взял в работу** |
| `confirmed → in_progress` | поставщик |
| `confirmed → shipped`, `in_progress → shipped` | поставщик |
| `shipped → received` | менеджер |
| `confirmed → rejected`, `in_progress → rejected` | поставщик, комментарий обязателен |
| `draft / confirmed / in_progress → cancelled` | менеджер |

#### Scenario: Состав правится только в черновике

- GIVEN заказ камней в состоянии `confirmed` или дальше
- WHEN менеджер пытается изменить строки таблицы «Запрошено»
- THEN изменение отклоняется

#### Scenario: Возврат в черновик до взятия в работу

- GIVEN заказ камней в состоянии `confirmed`, поставщик его ещё не взял
- WHEN менеджер нажимает «Вернуть в черновик»
- THEN состояние становится `draft`, состав снова редактируется

#### Scenario: После взятия в работу — только отмена

- GIVEN заказ камней в состоянии `in_progress`
- WHEN менеджер пытается вернуть его в черновик
- THEN действие отклоняется, доступна только отмена и создание нового документа

#### Scenario: Стадия «В обработке» необязательна

- GIVEN заказ камней в состоянии `confirmed`
- WHEN поставщик сразу отмечает отгрузку
- THEN состояние становится `shipped` — цепочка не требует промежуточной стадии

#### Scenario: Отклонение требует комментария

- GIVEN заказ камней в состоянии `confirmed` или `in_progress`
- WHEN поставщик отклоняет заявку без комментария
- THEN действие отклоняется

### Requirement: Отметка последнего изменения для опроса

Поставщик опрашивает Odoo и должен видеть, что в документе поменялось с прошлого раза.
Опрос идёт по полю `last_change_at`, **не по служебному `write_date`**.

Почему не `write_date`: строки таблиц — отдельные записи со своим `write_date`, и правка
строки родительский документ не трогает. Причём поведение зависит от способа записи —
правка в форме сохраняется через родителя и `write_date` документа обновляет, а запись
напрямую в модель строки (по API, из кода, серверным действием) нет. То есть при ручной
проверке всё выглядит рабочим, а ломается ровно на том пути, которым ходит интеграция.

Явное поле решает и вторую задачу: мы сами решаем, что считать изменением, и поставщик
не дёргается на исправленную опечатку в примечании.

**Обновляют** `last_change_at`: переход состояния; создание, изменение и удаление строк
запроса и строк отгрузки; отметка выбытия; проведение возврата.

**Не обновляют**: правка `notes`, сообщения в чаттере, изменение `fetched_at`.

**Точность — одна секунда.** `fields.Datetime.now()` в Odoo отбрасывает микросекунды, то
есть два изменения в одну секунду неразличимы. Поэтому опрашивающая сторона обязана
запрашивать `last_change_at >= since`, а не `>`, и переживать повторное чтение того же
документа. Со строгим `>` изменение, случившееся в ту же секунду, что и прошлый опрос,
теряется навсегда. Это требование к опросу, и оно идёт в сопроводительную записку.

#### Scenario: Правка строки видна поставщику

- GIVEN подтверждённый заказ камней
- WHEN изменяется строка отгрузки — например, проведён возврат и проставлено
  `disposal = returned`
- THEN `last_change_at` документа обновляется
- AND при следующем опросе поставщик видит документ как изменившийся

#### Scenario: Правка примечания поставщика не касается

- GIVEN подтверждённый заказ камней
- WHEN менеджер меняет `notes`
- THEN `last_change_at` не меняется

#### Scenario: Запись напрямую в строку, минуя форму

- GIVEN строка отгрузки, изменённая вызовом `write` на самой строке
- WHEN проверяется документ
- THEN `last_change_at` обновлён, несмотря на то что `write_date` документа не изменился

### Requirement: Оплата камней

Правило по умолчанию: **клиент заказа ремонта = поставщик камней → не оплачиваем**,
иначе оплачиваем. У складского заказа клиента нет — всегда оплачиваем.

Это значение по умолчанию при создании, **не вычисляемое поле**: менеджер может его
изменить, и последующие пересчёты не должны затирать его выбор.

#### Scenario: Заказ самого поставщика

- GIVEN заказ ремонта, клиент которого — SupplierX
- WHEN создаётся заказ камней с поставщиком SupplierX
- THEN `stones_payable = no`

#### Scenario: Камни поставщика в заказе стороннего клиента

- GIVEN заказ ремонта клиента «Ювелирный дом»
- WHEN создаётся заказ камней с поставщиком SupplierX
- THEN `stones_payable = yes`

#### Scenario: Ручной выбор менеджера не затирается

- GIVEN заказ камней, где менеджер вручную сменил `stones_payable`
- WHEN в заказе ремонта меняется клиент
- THEN `stones_payable` остаётся тем, что выбрал менеджер

### Requirement: Комиссия выражается базой и маржой

Поставщик даёт продажную цену клиенту. Клиент платит эту цену, поставщику уходит цена за
вычетом нашего процента. Отдельного понятия «комиссия» в данных нет — те же три величины,
что на строке услуги: выручка `subtotal`, база `supplier_amount`, маржа — их разница.

`commission_pct` снимается в документ при создании: договорённости меняются, а по прошлым
поставкам должно остаться действовавшее тогда.

### Requirement: Частичная отгрузка

Один документ — одна отгрузка. Недостача не блокирует получение, но обязана быть заметна
до того, как менеджер отметит «Камни получены».

Полнота вычисляется сопоставлением таблиц по `request_line_id`. **Известное ограничение:**
на мелочи расчёт неточен — она идёт агрегатом, и часть строк поставщик может добавить без
привязки к строке запроса.

#### Scenario: Отгружено меньше запрошенного

- GIVEN запрошено 12 камней, отгружено 8
- WHEN поставщик отмечает отгрузку
- THEN `shipped_complete = False`
- AND в форме документа и в заказе ремонта видна пометка о неполной отгрузке

#### Scenario: Запрос остатка

- GIVEN полученный заказ камней с неполной отгрузкой
- WHEN менеджер нажимает «Запросить остаток»
- THEN создаётся новый заказ камней в черновике, заполненный недостающим,
  с тем же поставщиком и заказом ремонта

### Requirement: Перенос камней в заказ ремонта

Действие доступно на полученном документе с `purpose = repair`. Перенос неразрушающий:
план остаётся в документе, повторный запуск обновляет, а не дублирует.

Цены в первой итерации не переносятся — до появления базы и маржи на строках камней.

#### Scenario: Сертифицированные камни разворачиваются по одному

- GIVEN отгружено 12 сертифицированных камней, каждый своей строкой
- WHEN менеджер нажимает «Перенести в заказ»
- THEN в заказе ремонта появляется 12 строк камней, по одной на камень,
  у каждой `quantity = 1` и свой сертификат

#### Scenario: Мелочь обновляет существующую строку

- GIVEN отгружена партия мелочи без сертификатов
- WHEN менеджер переносит её в заказ
- THEN обновляются количество и вес соответствующей строки камней заказа

#### Scenario: Повторный перенос не дублирует

- GIVEN перенос уже выполнялся
- WHEN менеджер нажимает «Перенести в заказ» ещё раз
- THEN строки, связанные через `stone_order_line_id`, обновляются, новые не создаются

#### Scenario: Предпросмотр перед применением

- GIVEN полученный заказ камней
- WHEN менеджер нажимает «Перенести в заказ»
- THEN сначала показывается, что будет добавлено, что обновлено и что не затронуто
- AND перенос выполняется только после подтверждения

### Requirement: Выбытие камня — возврат и бой

#### Scenario: Возврат поставщику

- GIVEN полученный заказ камней с оплачиваемыми камнями
- WHEN оформлен и проведён документ возврата на часть строк
- THEN эти строки помечаются `disposal = returned`
- AND сумма к оплате поставщику уменьшается на их `supplier_amount`

#### Scenario: Бой камня при закрепке

- GIVEN полученный камень
- WHEN менеджер отмечает `disposal = broken`
- THEN обязательно заполняется `broken_charge_to` — единого правила нет, решает
  руководитель

### Requirement: Что мы видим по камням

#### Scenario: Камни под заказы ремонта

- GIVEN полученные заказы камней с `purpose = repair`
- WHEN открыт список «Камни под заказы»
- THEN видны строки отгрузки без выбытия и без переноса в заказ, с группировкой
  по заказу ремонта

#### Scenario: К оплате поставщику

- GIVEN полученные заказы камней с `stones_payable = yes`
- WHEN открыт список «К оплате поставщику»
- THEN видна сумма `supplier_amount` по документам, ещё не вошедшим в счёт поставщика,
  с группировкой по поставщику

### Requirement: Заказ камней виден в заказе ремонта

#### Scenario: Кнопка-счётчик

- GIVEN заказ ремонта, по которому созданы два заказа камней
- WHEN менеджер открывает заказ
- THEN видит кнопку «Заказы камней: 2» и состояние последнего
- AND по клику открывается их список
