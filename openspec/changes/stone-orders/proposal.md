## Intent

Мастерская заказывает камни у поставщиков: SupplierX (поставщик бриллиантов со своей складской системой) и другие.
Сейчас это переписка в мессенджере — что запросили, что отгрузили, сколько должны,
нигде не зафиксировано.

Нужен документ, который ведёт всю цепочку: запросили → поставщик собрал → отгрузил →
получили → перенесли в заказ ремонта → рассчитались.

## Откуда взялась задача и почему спека не равна ТЗ

Отправная точка — ТЗ от поставщика SupplierX: интеграция его складской
системы с нашей Odoo по JSON-RPC.

Автор ТЗ не разработчик, ТЗ — скелет: он описал, **какая информация ему нужна и какую он
готов отдавать**, в терминах, которые предположил (поля `x_supplier_*` прямо на нашем заказе
ремонта, права SupplierX на запись в строки камней, «документ выдачи DL» как источник данных
о металле).

Мы берём из ТЗ предметную часть — состав информации и последовательность шагов, — а
способ реализации выбираем сами. Работающую систему под предположения скелета не
переделываем.

Разбирая ТЗ, обнаружили главное: **обмен с SupplierX — частный случай.** Заказ камней
поставщику нужен сам по себе, для любого поставщика и без всякого API. Поэтому:

- **слой 1 (эта спека)** — документ «Заказ камней», работает руками, с любым поставщиком;
- **слой 2 (`supplier-exchange`)** — API поверх него для тех поставщиков, у кого он есть.

Первый слой можно запустить и обкатать на живых заказах, не дожидаясь, пока поставщик
что-то напишет у себя.

## Модель

Модель `jewelry.stone.order`, UI — «Заказ камней», нумерация **`GO2026-NNNN`** (Gem Order,
в стиле существующих `RO` и `DL`). Вариант `SO` отвергнут: в мире Odoo читается как
Sales Order.

**Модулей два:** документ отдельно, обмен с SupplierX отдельно. Документ можно ставить без
интеграции — например в филиале без такого поставщика.

### Шапка документа

| Поле | Назначение |
|---|---|
| Поставщик | контрагент. SupplierX — один из |
| Назначение | под заказ ремонта / на склад |
| Заказ ремонта | ссылка, **необязательная** — у складского заказа её нет |
| Состояние | см. ниже |
| Оплата камней | «оплачиваем» / «заказ поставщика, не оплачиваем» |
| Процент комиссии | снимок на момент создания, по умолчанию из настройки поставщика |
| Накладная поставщика | номер, формат любой (у SupplierX — `PR-…`) |
| Забран поставщиком | отметка времени, автоматически при первом чтении по API |
| Отгружено полностью | вычисляется сопоставлением таблиц, см. «Частичная отгрузка» |

Комментарии — в чаттер документа, не в перезаписываемое поле. В ТЗ под это был один
`Char` (`x_supplier_note`), затираемый каждой новой записью; здесь сохраняется вся история
с автором и временем.

### Две таблицы, а не две колонки

| Таблица | Кто заполняет | Состав |
|---|---|---|
| **Запрошено** | менеджер, в черновике | тип камня, происхождение, форма огранки, размер (мм), количество, вес ct, сертификат (необязательно) |
| **Отгружено** | поставщик по API или менеджер руками | номер сертификата, фактический вес, количество, цена клиенту, ссылка на строку запроса (необязательная) |

Почему две таблицы, а не колонки «запрошено / отгружено» в одной строке: строка запроса —
это **требование** («маркиз 5×3 мм, 12 шт, 0.1692 ct»), а отгрузка сертифицированных
камней разворачивается в 12 записей, у каждой свой номер и свой вес. В одну строку это
не складывается. Попутно:

- права становятся тривиальными: поставщик пишет только во вторую таблицу;
- «склад добавил то, чего не просили» и «строку не закрыли» перестают быть краевыми
  случаями — просто нет соответствия;
- расхождение план/факт видно глазами.

**Сертификат — всегда на один камень.** Партийных сертификатов не бывает, поэтому строка
с заполненным сертификатом обязана иметь количество 1. Ограничение жёсткое, в обеих
таблицах: оно ловит ошибку ввода, из-за которой двенадцать камней уехали бы под одним
номером.

Цвет и чистота на строке запроса не заводятся — тип, форма, размер и происхождение
описывают требование достаточно, остальное идёт комментарием.

### Происхождение камня — обязательное поле

Натуральный или выращенный. Сейчас происхождение у нас есть **только внутри сертификата**
(`jewelry.gem.certificate.origin`), а у мелочи сертификата нет — сказать негде.

Это не атрибут, а **требование к поставщику**: менеджер запрашивает натуральный камень,
склад не должен подставить выращенный. Разница в цене — порядок величины, ошибка дорогая
в обе стороны. Поэтому поле обязательное.

Альтернатива — завести отдельный тип камня («Бриллиант» / «Бриллиант лабораторный»)
вместо поля. Дешевле, но задваивает справочник и ломает правила закрепки
(`jewelry.gem.setting.rule`), привязанные к типу с диапазонами веса. Выбрано поле.

## Состояния

| # | Состояние | Кто переводит | Что означает |
|---|---|---|---|
| 1 | `draft` — Черновик | менеджер | документ создан, состав правится |
| 2 | `confirmed` — Подтверждён | менеджер | состав зафиксирован, документ виден поставщику |
| 3 | `in_progress` — В обработке | поставщик | человек на складе взял в работу |
| 4 | `shipped` — Отгружен | поставщик | отгрузил, указал накладную и состав |
| 5 | `received` — Камни получены | менеджер | физически получил |
| — | `rejected` — Отклонён | поставщик | камней нет, комментарий обязателен |
| — | `cancelled` — Отменён | менеджер | |

Правила:

- **Правка состава — только в черновике.** Вернуть из «Подтверждён» в черновик можно,
  пока поставщик не взял в работу; после — только отмена и новый документ. Иначе склад
  собирает по одному списку, а у нас на экране другой. (В ТЗ было «повторное нажатие
  разрешено, даже если уже отгружено» — это гонка состояний.)
- **Переход «Подтверждён → Отгружен» напрямую разрешён.** Стадия «В обработке» ставится
  кнопкой на стороне поставщика — а её может не быть. Если сделать стадию обязательной,
  обмен встанет на пустом месте.
- **Отклонение возможно** из «Подтверждён» и «В обработке», после отгрузки — нет.
  Состояние конечное; документ остаётся в истории с причиной.
- **Отметка «Забран поставщиком»** — не стадия, а время. Иначе менеджер увидит подряд
  «Получен складом» и «В обработке» и не поймёт разницу. Как время она отвечает на
  вопрос «запрос вообще до них дошёл или у них опрос упал».

### Частичная отгрузка

Один документ — одна отгрузка. Отгрузили 8 из 12 — документ закрывается, недостача видна
как разница между таблицами. Нужен остаток — кнопка «Запросить остаток» создаёт второй
документ, заполненный недостающим.

Отвергнут вариант «документ ждёт дозагрузки»: накладная одна на документ, при нескольких
отгрузках она превращается в таблицу, состояние начинает ходить по кругу, получение
становится многократным. Много сложности ради случая, который решается одной кнопкой.
Каждая физическая посылка получает свой документ и свою накладную — что и есть правда.

Два следствия:

1. **«Отгружен» ≠ «отгружен полностью».** Полноту считаем сами, сопоставляя таблицы
   «Запрошено» и «Отгружено» — отдельной отметки у поставщика не требуем.
   _Известное ограничение:_ на мелочи сопоставление будет неточным — она идёт агрегатом,
   и часть строк поставщик может добавить без привязки к строке запроса. Решение принято
   сознательно: не нагружать поставщика лишним полем. Если на практике расчёт начнёт
   врать, вернёмся к явной отметке.
2. **Недостача должна быть заметна до отметки «Камни получены»**, иначе менеджер примет
   коробку, отметит получение, а ювелир обнаружит нехватку за верстаком.

## Оплата и комиссия

### Кто за камни платит

> клиент заказа ремонта = поставщик камней → это его заказ, не оплачиваем
> иначе → оплачиваем

Работает для любого поставщика: заказ SupplierX + камни SupplierX → не платим; заказ SupplierX + камни
стороннего поставщика → платим поставщику, SupplierX платит нам; заказ клиента + камни SupplierX →
платим SupplierX. У складского заказа клиента нет — всегда оплачиваем.

Это **значение по умолчанию, а не вычисляемое поле**: менеджер может поменять, и
пересчёт не должен затирать его выбор. Поменяли клиента в заказе позже — в документе
осталось как было. Документ снимок.

Отдельный флаг «внутренний / внешний заказчик» на контрагенте для этого не нужен:
сравнение двух партнёров живёт внутри документа. Если такой флаг понадобится для
отчётности — заводим отдельно и по своим причинам.

### Комиссия

Схема (A): поставщик даёт **продажную цену клиенту** со своими наценками; клиент платит
эту цену; поставщику отдаём её за вычетом нашего процента. Мы зарабатываем на том, что
продаём его камни.

Выражаем в терминах уже разрабатываемого механизма наценок, **не заводя отдельного
понятия «комиссия»**:

| Величина | Что это |
|---|---|
| Выручка | цена клиенту от поставщика |
| База | что отдаём поставщику = цена минус процент |
| Маржа | наш процент |

Те же три величины, что появились на строке услуги (`base_price` / `base_amount` /
`margin`) и распространяются сейчас на металл и камни. Иначе в P&L будет два названия
одного и того же, и через полгода никто не вспомнит, чем «комиссия по камням» отличается
от «маржи по камням».

Процент снимается в документ снимком: договорённости меняются, а по прошлым поставкам
должно остаться действовавшее тогда.

### Расчёт с поставщиком — не отчёт

«Сколько мы должны поставщику» — это **счёт поставщика** (`account.move` типа
`in_invoice`). Тогда даром достаётся то, чего в самописном отчёте не будет: возраст
задолженности, частичные платежи, сверка, сальдо контрагента — всё в стандартных местах.
Наш доход с камней — обычная маржа по этим позициям, тоже не отчёт.

Свой реестр «сколько должны» создал бы параллельный учёт кредиторки рядом со
стандартным. На проде уже был болезненный эпизод ровно такого рода — расхождение кассы и
P&L из-за расходов, живших мимо стандартного контура.

Целевая форма: периодический свод полученных заказов камней → счёт поставщика, то есть
`billing.batch` наоборот. Механика отбора «что уже вошло в расчёт, что ещё нет» там
отлажена, изобретать второй раз не нужно.

**В первую итерацию расчёт не входит** — только хранение цены и процента. Целевая форма
записана, чтобы не начать строить реестр долгов.

## Перенос в заказ ремонта

После «Камни получены» в документе лежит факт (сертификаты, веса, количества, цены), а
во вкладке Stones заказа — план менеджера. Нужна кнопка «Перенести в заказ».

Механика будет дорабатываться на практике, поэтому v1 должен быть **неразрушающим**:

1. **Ссылка с камня в заказе на строку документа.** Повторное нажатие обновляет, а не
   плодит дубли; видно происхождение каждого камня; при отладке понятно, что натворил
   перенос.
2. **Предпросмотр «что изменится»** перед применением: что добавится, что обновится, что
   не тронем.
3. **План остаётся в документе** и не затирается — откатиться всегда есть к чему.

Правило формы (вскроется сразу): `certificate_id` на строке камня заказа — **один на
строку**, поэтому перенос сертифицированных камней разворачивает одну строку запроса в N
строк заказа, по штуке на камень. Мелочь наоборот — обновляет количество и вес
существующей строки. Два разных правила в одной кнопке.

Последствия дальше по цепочке (увидим на живых заказах): «Generate Setting Services»
начнёт видеть 12 строк вместо одной, портал покажет 12 строк с сертификатами, в счёт
уйдёт 12 позиций.

**Цены переносятся только после того, как база и маржа появятся на строках камней** — см.
зависимости. Перенос цены должен включать `include_in_invoice`, иначе цена приедет и
никуда не пойдёт: у камней галочка по умолчанию выключена.

## Выбытие камня: возврат и бой

Камень может уйти не в изделие. Два разных случая, два разных механизма.

**Возврат поставщику — отдельный документ возврата** со своей накладной, со ссылкой на
исходный заказ камней и составом возвращаемого. Входит в первую итерацию: по
оплачиваемым камням возврат уменьшает долг, а без оформления долг будет завышен.

**Бой камня при закрепке — отметка на строке полученного камня**, с указанием, на кого
списано: брак мастерской, клиент или поставщик. Единого правила нет, **решает
руководитель** — случаи разные, и автоматика здесь навредит.

**Отмена заказа ремонта после того, как камни уехали** — тоже решение руководителя:
либо возврат документом, либо камни остаются у нас и идут в следующий заказ. Оба пути
доступны, система не выбирает за человека.

## Что мы видим по камням

Три вопроса, на которые контур обязан отвечать:

| Вопрос | Откуда | Итерация |
|---|---|---|
| Какие камни под какие заказы ремонта | строки «Отгружено» документов с заказом ремонта, в состоянии «Получены» | 1 |
| Какие камни просто на складе | остаток по складским документам | 2 |
| Сколько должны поставщику | суммы полученных документов с «оплачиваем», по которым ещё не выставлен счёт | 1 — сводка, 2 — счёт |

«Сколько должны» в первой итерации — **конвейерная сводка**, зеркало `billing.batch`
на клиентской стороне: «получено, но ещё не выставлено». Как только появится счёт
поставщика, цифра уходит в обычную кредиторку Odoo, и параллельного реестра долгов не
возникает.

Расход складского камня — это **перенос его в заказ ремонта**. Ссылка с камня в заказе
на строку документа, заложенная ради неразрушающего переноса, работает и как расход.
Одна связь на две задачи.

## Scope

### В scope первой итерации

1. Новый модуль, документ «Заказ камней» со всем вышеописанным
2. Кнопка «Заказать камни» в заказе ремонта + собственное меню документов
3. Кнопка «Запросить остаток»
4. Блок в заказе ремонта — кнопка-счётчик «Заказы камней: N» со списком, рядом состояние
   последнего. Только чтение
5. Признак происхождения камня на строке запроса **и** на строке камня заказа ремонта
6. Перенос в заказ (без цен — до готовности задачи по наценкам)
7. Документ возврата поставщику
8. Отметка боя камня с указанием, на кого списано
9. Сводка «камни под заказы» и «к оплате поставщику»
10. `ru.po`, тесты

### Вторая итерация

- **Склад камней** — каталог позиций, лоты, остатки, суммовой учёт, расход в заказ,
  закупка ходовых позиций без привязки к конкретному заказу. Приход берётся из строк
  «Отгружено» полученных документов первой итерации: шов проектируем сейчас, реализуем
  потом.
- **Расчёт с поставщиком** — свод за период → счёт поставщика.

Отложено сознательно: сначала нужно запустить обмен и обкатать его на живых заказах.
Пока всё согласуется, переделок будет много, и склад, построенный на несогласованном
документе, пришлось бы переделывать вместе с ним.

### Вне scope

- Изменение существующего контура заказа, выдачи и биллинга

## Зависимости от соседних задач

- **Наценки на услуги, металл и камни** (в работе в основной ветке) — от неё зависит
  перенос цен. Порядок: сначала она, потом перенос цен. Документ и цепочка состояний от
  неё не зависят и делаются параллельно.
- **Поле происхождения на `jewelry.repair.gem.line`** — небольшое изменение в
  `jewelry_repair_base`, за пределами нового модуля.
- **Склад камней (вторая итерация)** — переиспользуем `jewelry_stock_components`: там уже
  есть приход от поставщика со ссылкой на счёт, лоты, себестоимость, расход в заказ
  ремонта и минимальный остаток. Не совпадают только единицы: он считает граммы и сплавы,
  камни — это штуки, караты и тип/форма/размер.
  _Наблюдение: модуль есть в репозитории и уже чинился под Odoo 17 (см. `DECISIONS.md`),
  но в таблице модулей `CLAUDE.md` его нет, папка в `openspec/changes/` не
  заархивирована, задачи не отмечены. Уточнить статус до второй итерации._

### Две единицы измерения — что нашлось в Odoo (RAG, 2026-09-24)

Камень считается **одновременно в штуках и в каратах**, причём карат на штуку у каждой
партии свой. Проверено по `odoo_core`:

- штатного механизма второй единицы в ядре Odoo 17 **нет**;
- `stock.move._check_uom` (`addons/stock/models/stock_move.py:586`) требует, чтобы единица
  движения была в той же категории, что единица продукта, — то есть с фиксированным
  коэффициентом. Для камней это структурно неверно;
- `weight` на движении (`stock_delivery`) — вес для доставки, не учётная величина;
- отслеживание `tracking = lot | serial` подходит и ложится на разделение «мелочь /
  сертифицированный камень», но считает только штуки;
- в OCA есть `stock_secondary_unit` под этот паттерн, но из OCA у нас вендорен только
  stub `date_range`.

**Вывод: повторяем собственный приём.** В `jewelry_stock_components` штуки живут в штатном
складе Odoo, а вес — дополнительными полями на `stock.lot` (`total_weight_g`,
`remaining_weight_g`, `cost_per_gram`). Для камней то же самое с каратами вместо граммов.

## Открытые вопросы

По первой итерации открытых вопросов не осталось — все решения приняты 2026-09-24 и
разнесены по разделам выше.

### Отложено до второй итерации (склад)

Решать при проектировании склада, но знать о них заранее:

- **Мелочь и сертифицированные — два разных режима учёта.** Мелочь: партия однородных
  камней, средняя себестоимость, осмысленная позиция каталога. Сертифицированный камень:
  индивидуальный актив со своей ценой, позиция каталога почти бессмысленна. В терминах
  Odoo — партионный и серийный учёт.
- **Списание карат из партии.** Партия 100 шт / 17 ct, расходуем 5 шт — списываем 0.85 ct
  средним или фактический вес, который никто не взвешивал? От ответа зависит, сойдётся ли
  склад по каратам вообще.
- **Оценка склада** — в проводки или управленческой цифрой. В `CLAUDE.md` «полноценная
  себестоимость» числится вне scope проекта; суммовой учёт камней задевает эту границу.
  Двигать можно, но сознательно и с записью в `DECISIONS.md`.
- **Объём каталога ходовых позиций** — десяток размеров мелочи или сотни комбинаций
  тип/форма/размер/качество. От порядка величины зависит, нужен ли генератор каталога.
- **Камни клиента на склад не приходуются** — действует правило «материалы клиента
  информационно, материалы мастерской на складе». Камни, вынутые из изделия при ремонте,
  тоже клиентские.

## Вопросы поставщику — сняты

Опросник не понадобился: 2026-09-24 прошли по всем вопросам и ответили сами. Решения:

| Вопрос из ТЗ | Решение |
|---|---|
| Содержимое сертификата | исходим из того, что приходят номер и данные; пришёл только номер — заводим заглушку, менеджер добивает руками |
| Сертификат на партию | не бывает, сертификат всегда на один камень → ограничение «количество 1» |
| Фактический вес мелочи | не спрашиваем; поле в таблице «Отгружено» есть, заполнит — хорошо |
| Смотреть или забирать | забирать по API, вопрос снят |
| «Чистый вес при выдаче» | вес металла в изделии: вес изделия минус вес камней |
| Фото готового изделия | заводим отдельное поле «фото готовой работы»; не заполнено — отдаём снимок при приёме |
| Отметка «взял в работу» | не спрашиваем, описываем в сопроводительной записке |
| Отметка полноты отгрузки | не требуем, считаем сами |
| Нет камней на складе | поддерживаем оба пути: отклонение целиком и частичную отгрузку |
| Отмена после отгрузки | решает руководитель: возврат документом или камни остаются у нас |

Вместо опросника поставщику нужна **сопроводительная записка** — что реализовать у себя.
