# ТЗ: регистр котировок металла и расчет цены металлических материалов

## 1. Назначение

Нужно добавить в систему отдельный контур котировок драгоценных металлов для управленческого ценообразования материалов мастерской.

Цель:
- знать актуальную цену металла на конкретный момент времени
- рассчитывать цену продажи металлических материалов в заказе на основе котировки
- не использовать статичную цену товара как основной источник цены для металла
- фиксировать в строке заказа итоговую цену, по которой материал был рассчитан
- сохранить гибкость для будущей перепроверки котировок на этапе выдачи заказа

## 2. Базовый принцип

Номенклатура материала и цена металла должны быть разделены.

Продукт отвечает:
- что это за тип материала или комплектующей

Регистр котировок отвечает:
- сколько стоит металл на конкретную дату и время

Строка материала заказа отвечает:
- по какой котировке и по какой цене материал был фактически рассчитан

## 3. Общая модель первой версии

Первая версия строится на трех уровнях:

1. Регистр котировок металла
- хранит историю изменения цен металлов

2. Шапка заказа ремонта
- хранит основную дату котировки заказа

3. Строка материала заказа
- по умолчанию наследует дату котировки из шапки
- по этой дате получает актуальную котировку
- рассчитывает и фиксирует цену строки

## 4. Новая сущность

Рекомендуемая модель:
- `jewelry.metal.rate`

Назначение:
- хранить историю изменения цен металла
- быть источником актуальной цены на момент расчета

## 5. Поля регистра котировок

Минимальный набор:
- `metal_id`
- `price_per_gram`
- `currency_id`
- `effective_at`
- `company_id`
- `notes`
- `active`

Опционально на следующем этапе:
- `source`
- `entered_by`
- `rate_type`

## 6. Логика актуальной котировки

Актуальной котировкой считается последняя запись регистра, удовлетворяющая условиям:
- тот же `metal_id`
- `effective_at <= момент расчета`
- сортировка по `effective_at desc, id desc`
- используется первая запись

Это и есть Odoo-аналог среза последних для данного контура.

## 7. Что именно котируется

В первой версии котировка хранится по базовому металлу:
- золото
- серебро
- платина
- палладий, если понадобится

То есть цена хранится не по товару и не по конкретному продукту, а по металлу.

## 8. Дата котировки в шапке заказа

В шапке заказа ремонта добавляется поле:
- `metal_rate_at`

Смысл поля:
- это основная дата и время котировки, принятые для данного заказа
- она задает общий ценовой контекст для металлических материалов заказа

Назначение:
- все строки металлических материалов по умолчанию рассчитываются в едином временном срезе
- менеджер видит, по какой дате котировки посчитан заказ

Правило заполнения по умолчанию:
- если пользователь не указал дату котировки вручную, `metal_rate_at` должно автоматически заполняться текущей датой и временем

## 9. Дата котировки в строке материала

В строке материала добавляется поле:
- `rate_datetime`

Правило:
- если `rate_datetime` не заполнено вручную, оно должно по умолчанию браться из `order_id.metal_rate_at`

Это позволяет:
- использовать общий контекст котировки из шапки заказа
- при необходимости задавать исключение для отдельной строки

## 10. Поля строки материала для котировочного контура

Для металлических материалов в строке должны существовать:
- `rate_datetime`
- `rate_price_per_gram`
- `price_unit`
- `subtotal`

Смысл:

`rate_datetime`
- по какой дате и времени выполнялся поиск котировки

`rate_price_per_gram`
- какая котировка металла была фактически применена

`price_unit`
- итоговая рассчитанная цена строки

`subtotal`
- итоговая сумма строки

## 11. Связь со сплавом

Если в строке заполнен `alloy_id`, цена рассчитывается через:
- металл из `alloy_id.metal_id`
- коэффициент чистоты из `alloy_id.purity`

Базовая формула:
- `alloy_price_per_gram = metal_rate.price_per_gram * purity`

Где:
- `metal_rate.price_per_gram` — цена чистого металла
- `purity` — коэффициент сплава

## 12. Расчет цены строки

Для металлических материалов цена строки должна рассчитываться не из `product.lst_price`, а из регистра котировок.

Базовый алгоритм:
1. определить металл по `alloy_id`
2. взять дату котировки:
   - сначала `rate_datetime` строки
   - если пусто, то `order_id.metal_rate_at`
3. найти актуальную котировку металла на этот момент
4. рассчитать цену 1 грамма сплава через purity
5. умножить на вес строки
6. записать результат в `price_unit`
7. сохранить использованную котировку в `rate_price_per_gram`

Базовая формула:
- `price_unit = metal_rate.price_per_gram * alloy_purity * weight`

## 13. Что сохраняется как факт

Даже если цена получается расчетом, в строке материала должны фиксироваться:
- дата котировки
- использованная котировка
- рассчитанная цена
- сумма строки

Это нужно потому, что:
- старые строки не должны самопроизвольно меняться после обновления регистра
- биллинг должен видеть фактическую цену строки
- управленческий анализ должен быть воспроизводимым

## 14. Момент фиксации цены

Рекомендуемый вариант первой версии:
- цена рассчитывается в момент заполнения металлической строки
- результат сохраняется в строке
- дальше не пересчитывается автоматически сам по себе

Если пользователь хочет применить новую котировку:
- это должно выполняться отдельным действием
- либо ручной корректировкой строки

При этом локальный автоматический пересчет строки допускается и должен выполняться, если пользователь вручную меняет параметры расчета конкретной строки.

В первой версии строка металлического материала должна автоматически пересчитываться при изменении:
- `rate_datetime`
- `alloy_id`
- `weight`

В таком пересчете должны обновляться:
- `rate_price_per_gram`
- `price_unit`
- `subtotal`

## 15. Поддержка нескольких изменений цены в день

Система должна поддерживать изменение цены несколько раз в течение дня.

Для этого:
- `effective_at` в регистре хранится с точностью до даты и времени
- `metal_rate_at` в заказе тоже хранится с датой и временем
- `rate_datetime` строки тоже хранится с датой и временем

## 16. Где применяется регистр

Регистр котировок применяется только для металлических материалов.

Не применять автоматически для:
- камней
- расходников
- неметаллических запчастей
- упаковки
- химии

Для них цена может по-прежнему браться:
- из товара
- или задаваться вручную

## 17. Базовые проверки

Система не должна рассчитывать цену металлической строки, если:
- не указан `alloy_id`
- не указан `weight`
- не указана дата котировки ни в строке, ни в шапке заказа
- для нужного металла нет актуальной котировки

В таких случаях система должна:
- явно сообщать пользователю, что расчет невозможен
- не подставлять фиктивную цену без подтверждения

## 18. Гибкость на будущее

На этапе выдачи заказа в будущем может потребоваться перепроверка котировок.

Система должна оставаться гибкой для сценариев:
- оставить старую цену без изменений
- сравнить старую и текущую котировку
- предложить пересчет
- пересчитать только часть строк
- потребовать подтверждение менеджера

В первой версии эти механизмы не реализуются, но архитектура должна им не мешать.

## 19. Что не включать в первую версию

Не включать сразу:
- автоматическую переоценку уже созданных заказов
- сложные наценки по продуктам и типам материалов
- внешние интеграции с биржами или API
- отдельные регистры по каждому сплаву
- сложную финансовую аналитику изменения котировок

## 20. Рекомендованное правило первой версии

- котировка металла хранится отдельно в регистре
- в шапке заказа хранится дата котировки заказа
- строка материала по умолчанию использует дату котировки из шапки
- строка может иметь собственную дату котировки как исключение
- цена металлической строки рассчитывается по котировке, сплаву и весу
- рассчитанная цена фиксируется в строке как факт
- система не пересчитывает старые строки автоматически массово без отдельного действия пользователя

## 21. UI-правило для таблицы материалов

В табличной части материалов основные рабочие поля должны идти в начале таблицы.

К основным рабочим полям относятся:
- материал
- сплав
- вес
- количество
- цена
- сумма

Все дополнительные и служебные поля должны добавляться в конец таблицы.

К таким полям относятся:
- описание
- операция
- дата котировки строки
- использованная котировка
- служебные флаги

Назначение этого правила:
- не перегружать пользователя на основном сценарии ввода
- сохранять удобство ручного заполнения
- при этом не терять управленческую детализацию
