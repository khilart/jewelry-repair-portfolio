# ТЗ: отдельный контур учета металла

## 1. Назначение

Нужно реализовать отдельный контур учета металла как самостоятельный модуль поверх текущей системы ремонта.

Назначение контура:
- учитывать остатки металла по сплавам
- учитывать место хранения сплава
- фиксировать движения металла собственным документом
- поддержать ручные и автоматические движения металла
- подготовить основу для автоматических приходов и списаний из заказов ремонта

На данном этапе объектом учета является:
- `alloy_id`
- `storage_id`
- `weight`

Базовое правило учета:
- в данном контуре учитывается только фактический вес металла
- технологические потери, возвратные потери и безвозвратные потери не входят в движения этого регистра
- для потерь будет реализован отдельный контур учета

На данном этапе не учитывается:
- форма хранения
- партия
- серийный номер
- бухгалтерская стоимость остатков

## 2. Архитектурное решение

Реализация выполняется отдельным модулем:
- `jewelry_metal_accounting`

Зависимость:
- `jewelry_repair_base`

Модели:
- `jewelry.metal.storage`
- `jewelry.metal.document`
- `jewelry.metal.document.line`
- `jewelry.metal.move`
- `jewelry.metal.document.log`

Источник правды по остаткам:
- регистр движений `jewelry.metal.move`

Остаток рассчитывается как агрегат движений по измерениям:
- `alloy_id`
- `storage_id`

## 3. Основные сущности

### 3.1. Metal Storage

Модель:
- `jewelry.metal.storage`

Назначение:
- место хранения металла

Минимальные поля:
- `name`
- `code`
- `active`
- `company_id`
- `responsible_user_id`
- `notes`

Примеры:
- Основной склад металла
- Производственный участок
- У мастера
- Сейф приемки

### 3.2. Metal Document

Модель:
- `jewelry.metal.document`

Назначение:
- пользовательский документ фиксации хозяйственной операции по металлу

Основные поля:
- `name`
- `operation_type`
- `state`
- `document_date`
- `company_id`
- `partner_id`
- `source_storage_id`
- `dest_storage_id`
- `notes`
- `amount_total`
- `line_ids`

Поля интеграции с источником:
- `source_model`
- `source_res_id`
- `source_ref`

Назначение полей интеграции:
- хранить документ-источник, который создал движение металла
- поддержать автоматическое создание документа из заказа ремонта и других будущих контуров

Примеры:
- `source_model = jewelry.repair.order`
- `source_res_id = 25`
- `source_ref = RO-00025`

### 3.3. Metal Document Line

Модель:
- `jewelry.metal.document.line`

Назначение:
- строка документа металла

Базовые поля:
- `document_id`
- `alloy_id`
- `weight`
- `rate_datetime`
- `rate_price_per_gram`
- `amount`
- `notes`

Дополнительные поля для переплавки:
- `output_alloy_id`
- `output_weight`
- `loss_weight`
- `conversion_ratio`

Редакционное решение первой версии:
- документ проектируется как многострочный
- но бизнес-сценарии MVP могут использовать одну основную строку

### 3.4. Metal Move

Модель:
- `jewelry.metal.move`

Назначение:
- регистр движений металла
- источник расчета остатков
- регистр только смысловых движений

Поля:
- `document_id`
- `document_line_id`
- `document_date`
- `operation_type`
- `company_id`
- `alloy_id`
- `storage_id`
- `weight_in`
- `weight_out`
- `signed_weight`
- `state`
- `source_model`
- `source_res_id`
- `source_ref`
- `notes`

Правило:
- `signed_weight` может быть вычисляемым как `weight_in - weight_out`
- остатки строятся по сумме `signed_weight`
- в регистре не создаются сторнирующие технические движения
- отмена документа не должна раздувать регистр дополнительными reversal-записями

Поля интеграции с источником в движении:
- дублируются из документа
- это нужно для удобной аналитики и поиска всех движений, созданных конкретным заказом ремонта

### 3.5. Metal Document Log

Модель:
- `jewelry.metal.document.log`

Назначение:
- отдельный журнал событий жизненного цикла документа

Поля:
- `document_id`
- `event_type`
- `event_datetime`
- `user_id`
- `message`
- `payload_json`

Примеры событий:
- создание документа
- изменение реквизитов
- проведение
- отмена
- возврат в черновик

## 4. Виды операций

В документе используется единое поле:
- `operation_type`

Допустимые значения:
- `receipt`
- `transfer`
- `writeoff`
- `remelt`

Это один тип документа с разной бизнес-логикой проведения.

## 5. Общие правила работы документа

Состояния:
- `draft`
- `posted`
- `cancel`

Правила:
- в `draft` документ редактируется
- при `posted` создаются записи регистра `jewelry.metal.move`
- после `posted` документ не должен свободно редактироваться
- `cancel` должен отменять учетный эффект документа без удаления аудита
- при `cancel` существующие движения документа выводятся из учета, но не заменяются reversal-движениями
- история изменений и отмен хранится в `jewelry.metal.document.log`

## 6. Бизнес-логика по операциям

### 6.1. Приход

Обязательные поля:
- `partner_id`
- `dest_storage_id`
- `alloy_id`
- `weight`
- `rate_datetime`

Система:
- определяет металл через `alloy_id`
- находит котировку по той же логике, что и в заказе ремонта
- считает информационную сумму

Формула суммы:
- `amount = metal_rate.price_per_gram * alloy.purity * weight`

При проведении:
- создается движение в плюс по комбинации `alloy_id + dest_storage_id + weight`

Важно:
- сумма хранится только в документе и строке документа
- сумма не участвует в расчете остатков

### 6.2. Перемещение

Обязательные поля:
- `source_storage_id`
- `dest_storage_id`
- `alloy_id`
- `weight`

При проведении:
- создается расход со склада-отправителя
- создается приход на склад-получатель

Проверки:
- `source_storage_id` и `dest_storage_id` не должны совпадать

Важно:
- недостаток текущего остатка не блокирует проведение документа
- система может показывать предупреждение или отрицательный остаток в аналитике, но не должна запрещать движение

### 6.3. Списание

Обязательные поля:
- `source_storage_id`
- `alloy_id`
- `weight`

Дополнительно рекомендуется:
- `writeoff_reason`

При проведении:
- создается расход по комбинации `alloy_id + source_storage_id + weight`

Важно:
- недостаток остатка не блокирует списание

### 6.4. Переплавка

Сценарий:
- один сплав преобразуется в другой

Минимальные поля:
- `source_storage_id`
- `dest_storage_id`
- `alloy_id`
- `weight`
- `output_alloy_id`
- `output_weight`
- `loss_weight`
- `conversion_ratio`

Базовое правило:
- входной сплав списывается
- выходной сплав приходуется

Баланс первой версии:
- допускается ручной ввод `output_weight`
- `loss_weight` может быть ручным или вычисляемым
- рекомендуется правило:
  - `weight = output_weight + loss_weight`

Важно:
- недостаток остатка не блокирует переплавку
- система должна позволять фиксировать преобразование даже при временно отрицательном остатке

## 7. Информационная сумма

Сумма нужна только как справочная информация в документе.

В первой версии:
- сумма рассчитывается только для прихода
- для перемещения, списания и переплавки сумма не является обязательной частью учета

Допускается в будущем:
- информационная оценка других операций

Но в MVP это не является обязательным требованием.

## 7.1. Правило по весу для движений

Для всех документов металл-контура:
- в движения регистра попадает только фактический вес строки
- расчетные веса потерь не должны увеличивать приход, расход, перемещение или переплавку

Это означает:
- если в ремонтном контуре есть `weight_loss` или другие расчетные показатели потерь, они не используются в `jewelry.metal.move`
- складской остаток по металлу должен отражать только реальный физический вес сплава

## 8. Правила расчета остатков

Остатки рассчитываются по регистру движений:
- приход увеличивает остаток
- расход уменьшает остаток

Измерения остатка:
- `alloy_id`
- `storage_id`

Дополнительно может использоваться срез:
- на дату
- по компании

Главное правило MVP:
- система должна уметь показывать текущий расчетный остаток
- система не должна блокировать документ, если после проведения остаток станет отрицательным
- в расчет остатков входят только движения в статусе `posted`

## 9. Интеграция с заказами ремонта

Контур должен поддерживать автоматическое создание документов движения металла из других бизнес-документов.

Первый целевой источник:
- `jewelry.repair.order`

Для этого в документе и движениях нужно хранить ссылку на документ-источник:
- `source_model`
- `source_res_id`
- `source_ref`

Смысл:
- можно понять, какой заказ ремонта создал приход или списание
- можно найти все движения, связанные с конкретным ремонтом
- можно избежать дублирования при повторной попытке автоматической генерации

Рекомендуемое поведение:
- автоматический документ металла создается как обычный `jewelry.metal.document`
- пользователь может открыть его из заказа ремонта
- документ сохраняет признак происхождения от ремонта

## 10. Интерфейсы

В модуле должны быть доступны:
- список и форма мест хранения
- список и форма документов движения металла
- список движений металла
- журнал событий документа
- базовый отчет остатков

В форме документа:
- поля шапки зависят от `operation_type`
- ненужные поля скрываются
- строки документа доступны в табличной части

В форме движения:
- движение открывается в основном как read-only регистр

В форме документа:
- должна быть отдельная вкладка с историей событий документа

## 11. Отчеты и контроль правильности движений

В модуле нужно предусмотреть отчетность по аналогии со складским учетом, чтобы пользователь мог проверить корректность работы документов и регистра.

Обязательные отчеты первой версии:
- ведомость остатков металла
- карточка движения металла
- журнал документов движения металла
- отчет по отрицательным остаткам

### 11.1. Ведомость остатков металла

Назначение:
- показать текущие и исторические остатки по металлу

Основные измерения:
- `storage_id`
- `alloy_id`
- `company_id`

Показатели:
- остаток на начало периода
- приход за период
- расход за период
- остаток на конец периода

Фильтры:
- по дате `на дату` или `за период`
- по месту хранения
- по сплаву
- по компании

Назначение отчета:
- основной инструмент проверки правильности регистра движений

### 11.2. Карточка движения металла

Назначение:
- детально показать хронологию движений по выбранному сплаву и месту хранения

Строки отчета:
- дата документа
- документ
- тип операции
- приход
- расход
- остаток после движения
- источник документа

Фильтры:
- по сплаву
- по месту хранения
- по периоду
- по документу-источнику

Назначение отчета:
- проверка, как конкретный документ повлиял на остаток
- разбор спорных ситуаций и аудит

### 11.3. Журнал документов движения металла

Назначение:
- список документов с основными реквизитами и статусом проведения

Колонки:
- номер
- дата
- тип операции
- контрагент
- склад-отправитель
- склад-получатель
- статус
- источник создания
- количество строк
- информационная сумма

Назначение отчета:
- контроль полноты ввода документов
- быстрый переход к первичному документу и связанным движениям

### 11.4. Отчет по отрицательным остаткам

Назначение:
- показать комбинации `сплав + место хранения`, где после проведения образовался отрицательный расчетный остаток

Поля:
- место хранения
- сплав
- текущий остаток
- дата первого ухода в минус
- последнее движение

Важно:
- отчет нужен именно как контрольный инструмент
- отрицательный остаток допустим по бизнес-правилу, но должен быть видим пользователю

### 11.5. Принципы построения отчетов

Отчеты должны строиться непосредственно по регистру `jewelry.metal.move`.

Главные правила:
- отчеты не должны считать остатки по документам напрямую, минуя регистр
- пользователь должен иметь возможность сверить документ, движения и остаток между собой
- в отчетах должна быть возможность открыть исходный документ движения
- в отчетах должна быть возможность увидеть документ-источник, например заказ ремонта
- в общие отчеты по движениям по умолчанию должны попадать только движения со статусом `posted`

## 12. Базовые проверки

Нужно валидировать:
- обязательные поля по типу операции
- корректность сплава
- положительный вес строки
- запрет одинакового склада отправителя и получателя для перемещения
- корректность заполнения полей переплавки

Не нужно блокировать:
- отрицательный остаток после проведения

Допускается:
- warning в UI
- отдельный отчет по отрицательным остаткам

## 13. Критерии приемки

Контур считается реализованным корректно, если:
- создан отдельный модуль `jewelry_metal_accounting`
- в системе есть справочник мест хранения металла
- можно создать документ движения металла с типом `receipt`
- можно создать документ движения металла с типом `transfer`
- можно создать документ движения металла с типом `writeoff`
- можно создать документ движения металла с типом `remelt`
- проведение документа создает записи в `jewelry.metal.move`
- остатки можно получить по паре `сплав + место хранения`
- приход рассчитывает информационную сумму по котировке и пробе
- сумма не влияет на количественные остатки
- перемещение создает расход и приход между местами хранения
- списание создает расход
- переплавка создает расход по входному сплаву и приход по выходному сплаву
- отрицательный остаток не блокирует проведение документа
- документ и движения хранят ссылку на бизнес-документ, который их создал
- архитектура позволяет автоматически создавать документы движения металла из заказов ремонта
- в документе доступен отдельный журнал событий
- отмена документа не создает reversal-движений в регистре
- в системе есть ведомость остатков металла
- в системе есть карточка движения металла
- в системе есть журнал документов движения металла
- в системе есть отчет по отрицательным остаткам
- по отчетам можно сверить остаток, документы и движения между собой

## 14. Следующий этап

Следующей итерацией можно добавить:
- автоматическую генерацию документов из заказов ремонта
- отдельный контур учета потерь металла
- отдельные правила для приходования металла от клиента и от поставщика
- инвентаризацию остатков металла
- отчет по отрицательным остаткам
- журнал движений по источнику документа
- настройку прав доступа по местам хранения
- более строгую модель переплавки с несколькими входными и выходными строками
