# ТЗ: контур учета металла в Jewelry Repair System

## 1. Назначение

Нужно сформировать единый контур учета металла для заказов ремонта в Odoo Community.

Цель контура:
- учитывать металл изделия клиента на входе и выходе
- учитывать металл, использованный мастерской в заказе
- хранить сплав как основной классификатор металла
- рассчитывать эквивалент чистого металла
- рассчитывать цену металлических материалов по котировке на дату заказа или строки
- подготовить основу для управленческой отчетности, биллинга и будущей складской логики по металлу

Этот документ объединяет требования, которые раньше были разнесены между общим ТЗ проекта, черновиком по материалам и отдельным ТЗ по котировкам металла.

## 2. Границы первой версии

В первую версию входят:
- справочники металлов и сплавов
- учет сплава и веса изделия в заказе ремонта
- учет металлических материалов в строках материалов заказа
- регистр котировок металла
- расчет цены металлических материалов по весу и пробе
- учет возвратных потерь металла в расчете цены строки материала
- фиксация фактически использованной котировки в строке материала
- базовые отчеты и аналитика по металлу на уровне заказа

В первую версию не входят:
- полноценный складской учет клиентского металла как отдельного актива
- возврат клиентского металла или лома
- автоматическое формирование складских движений по драгоценному металлу
- отдельный бухгалтерский контур драгметаллов
- внешние интеграции с биржами, банками или API котировок
- автоматическая массовая переоценка старых заказов
- сложные технологические нормы, плавка, аффинаж и переработка отходов

## 3. Роль контура в системе

Контур учета металла должен отвечать на вопросы:
- из какого сплава было изделие клиента при приемке
- сколько изделие весило при приемке и при выдаче
- какова разница веса
- каков эквивалент чистого металла по изделию
- сколько металла мастерская использовала в заказе
- какой сплав использовался в строках материалов
- по какой котировке и по какой цене были рассчитаны металлические материалы
- какой суммарный вес и эквивалент чистого металла сейчас находится у каждого держателя изделия

## 4. Связанные документы

Контур должен быть согласован со следующими документами:
- `chatgpt.md`
- `MATERIALS_SPEC_DRAFT.md`
- `METAL_RATES_SPEC.md`

Если между документами есть расхождение, приоритет для реализации этого контура имеет данный документ как сводный.

## 5. Основные сущности

### 5.1. Metal

Модель:
- `jewelry.metal`

Назначение:
- базовый классификатор металлов

Минимальные поля:
- `name`
- `code`
- `active`

Примеры:
- Gold
- Silver
- Platinum

### 5.2. Metal Alloy

Модель:
- `jewelry.metal.alloy`

Назначение:
- справочник проб и сплавов

Минимальные поля:
- `name`
- `code`
- `metal_id`
- `purity`
- `active`

Правила:
- в заказе и в строке материала пользователь выбирает именно `alloy_id`
- `metal_id` в прикладных документах определяется через сплав
- `purity` хранится коэффициентом, например `0.585`, `0.750`, `0.925`, `0.999`

### 5.3. Metal Rate

Модель:
- `jewelry.metal.rate`

Назначение:
- хранить историю котировок металлов

Минимальные поля:
- `metal_id`
- `price_per_gram`
- `currency_id`
- `effective_at`
- `company_id`
- `notes`
- `active`

Правило актуальной котировки:
- используется последняя запись, где `effective_at <= момент расчета`
- сортировка: `effective_at desc, id desc`

### 5.4. Repair Order

Модель:
- `jewelry.repair.order`

Назначение в металл-контуре:
- хранить характеристики металла по принятому изделию
- хранить общий временной срез котировки для металлических материалов заказа

Поля металл-контура:
- `alloy_id`
- `metal_id`
- `received_weight`
- `delivered_weight`
- `weight_delta`
- `fine_weight_received`
- `fine_weight_delivered`
- `metal_rate_at`

### 5.5. Repair Material Line

Модель:
- `jewelry.repair.material.line`

Назначение:
- хранить фактически использованные материалы мастерской в заказе
- быть основной единицей учета металлических расходных строк

Поля металл-контура:
- `order_id`
- `order_operation_id`
- `product_id`
- `quantity`
- `uom_id`
- `weight`
- `weight_loss`
- `alloy_id`
- `rate_datetime`
- `rate_price_per_gram`
- `price_unit`
- `subtotal`
- `include_in_invoice`
- `consume_from_stock`
- `description`

Связанные настройки продукта:
- `repair_material_return_loss_percent`
- `repair_material_nonreturn_loss_percent`

## 6. Металл и вес изделия клиента

### 6.1. Логика шапки заказа

При приемке изделия пользователь должен иметь возможность заполнить:
- сплав изделия
- вес изделия при приемке

При выдаче изделия пользователь должен иметь возможность заполнить:
- вес изделия при выдаче

Система должна автоматически рассчитывать:
- `weight_delta = delivered_weight - received_weight`
- `fine_weight_received = received_weight * purity`
- `fine_weight_delivered = delivered_weight * purity`

### 6.2. Правила заполнения

Правила:
- `metal_id` в заказе не вводится вручную
- `metal_id` должен быть related или вычисляемым от `alloy_id.metal_id`
- без `alloy_id` эквивалент чистого металла не рассчитывается
- изменение `alloy_id`, `received_weight` или `delivered_weight` должно пересчитывать производные показатели

### 6.3. Назначение этих данных

Данные о весе изделия нужны для:
- контроля изменения веса между приемкой и выдачей
- отчетности по суммарному весу изделий в работе
- отчетности по эквиваленту чистого металла
- подготовки к будущему контуру себестоимости и металл-аналитики

## 7. Металл в строках материалов

### 7.1. Принцип модели

Материалы принадлежат заказу ремонта.

Правила:
- каждая строка материала обязательно связана с `order_id`
- связь с `order_operation_id` является дополнительной детализацией
- одна строка материала существует в единой модели строк заказа
- нельзя вводить отдельные несвязанные наборы материалов заказа и материалов операции

### 7.2. Смысл полей

`quantity`
- товарно-складской смысл строки

`weight`
- фактический вес использованного материала
- для металлических материалов это ключевое поле

`weight_loss`
- расчетный вес возвратных потерь
- вычисляется автоматически по проценту возвратных потерь из продукта
- участвует в расчете стоимости строки

`alloy_id`
- фактический сплав использованного материала
- не обязан совпадать со сплавом изделия клиента

`rate_datetime`
- дата и время котировки, по которым рассчитывается цена металлической строки

`rate_price_per_gram`
- фактически использованная котировка чистого металла

`price_unit`
- итоговая цена единицы строки

`subtotal`
- сумма строки

### 7.3. Правила по умолчанию

При создании строки материала:
- `uom_id` подставляется из продукта
- `description` подставляется из продукта
- `alloy_id` по умолчанию подставляется из `order_id.alloy_id`
- `rate_datetime` по умолчанию подставляется из `order_id.metal_rate_at`
- `include_in_invoice` и `consume_from_stock` подставляются из настроек продукта
- процент возвратных и безвозвратных потерь берется из продукта

Если строка создается из операции:
- `order_id` должен определяться автоматически из `order_operation_id.order_id`
- система должна проверять, что операция принадлежит тому же заказу

### 7.4. Обязательность веса

Для металлических материалов поле `weight` должно быть обязательным.

Способ определения металлической строки в первой версии:
- через настройку продукта
- продукт должен позволять явно указать, что для него вес обязателен

### 7.5. Потери металла

Для продукта ремонтного материала должны храниться:
- `repair_material_return_loss_percent` — процент возвратных потерь
- `repair_material_nonreturn_loss_percent` — процент безвозвратных потерь

В строке материала должен вычисляться показатель:
- `weight_loss = weight * repair_material_return_loss_percent / 100`

Правила первой версии:
- `weight_loss` вычисляется автоматически и не вводится вручную
- `weight_loss` пересчитывается при изменении `weight` или `product_id`
- в формуле цены участвует только возвратная часть потерь
- процент безвозвратных потерь пока хранится в продукте как технологический параметр и не участвует в расчете цены строки

## 8. Контур котировок и расчет цены

### 8.1. Базовый принцип

Цена металлического материала не должна браться из `product.lst_price` как из основного источника истины.

Для металлических строк цена рассчитывается из:
- базового металла
- пробы сплава
- веса строки
- веса возвратных потерь
- котировки на заданную дату и время

### 8.2. Источник даты котировки

В заказе есть общее поле:
- `metal_rate_at`

В строке материала есть поле:
- `rate_datetime`

Правило:
- если у строки заполнен `rate_datetime`, используется он
- если не заполнен, используется `order_id.metal_rate_at`

### 8.3. Формула расчета

Если в строке заполнены `alloy_id`, `weight` и доступна котировка:

- `alloy_price_per_gram = metal_rate.price_per_gram * alloy.purity`
- `weight_loss = weight * return_loss_percent / 100`
- `pricing_weight = weight + weight_loss`
- `line_total_price = alloy_price_per_gram * pricing_weight`
- `price_unit` определяется из итоговой суммы строки с учетом `quantity`

В строке обязательно фиксируются:
- фактическая дата расчета
- котировка чистого металла
- рассчитанная цена
- рассчитанная сумма

### 8.4. Когда выполняется пересчет

В первой версии строка металлического материала должна пересчитываться при изменении:
- `alloy_id`
- `weight`
- `quantity`
- `rate_datetime`
- `order_id`, если от него наследуются значения по умолчанию
- `product_id`, если он меняет процент возвратных потерь

Обновляться должны:
- `weight_loss`
- `rate_price_per_gram`
- `price_unit`
- `subtotal`

### 8.5. Что нельзя делать молча

Система не должна молча подставлять фиктивную цену, если:
- не указан `alloy_id`
- не указан `weight`
- не указана дата котировки ни в строке, ни в шапке заказа
- для нужного металла нет котировки на момент расчета

В таких случаях система должна:
- явно сообщать пользователю о причине
- не считать строку рассчитанной по металлу

## 9. Разделение контуров клиента и мастерской

Нужно четко разделить два вида металл-данных.

Металл изделия клиента:
- это характеристика принятого изделия
- хранится в шапке заказа
- используется для контроля веса, движения и аналитики

Металл мастерской:
- это фактически использованный материал
- хранится в строках материалов заказа
- используется для цены, счета и будущего списания

Главное правило:
- сплав изделия и сплав использованного материала могут отличаться
- система не должна принудительно их синхронизировать после создания строки материала

## 10. Интерфейсы

### 10.1. Форма заказа

На форме заказа должны быть доступны:
- `alloy_id`
- `received_weight`
- `delivered_weight`
- `metal_rate_at`
- вычисляемые поля `metal_id`, `weight_delta`, `fine_weight_received`, `fine_weight_delivered`
- табличная часть `material_line_ids`

### 10.2. Таблица материалов

В строках материалов заказа должны быть видны:
- материал
- сплав
- количество
- единица измерения
- вес
- вес возвратных потерь
- дата котировки
- котировка за грамм
- цена
- сумма
- флаги счета и складского списания
- связанная операция при наличии

### 10.3. Справочники

Отдельно должны быть доступны меню и формы для:
- металлов
- сплавов
- котировок металлов

## 11. Отчетность

Первая версия должна позволять построить как минимум следующие управленческие срезы:
- общий вес изделий в работе
- общий эквивалент чистого металла по изделиям в работе
- общий вес изделий у текущего держателя
- общий эквивалент чистого металла у текущего держателя
- расход металлических материалов по заказам
- расход металлических материалов по сплавам
- список строк материалов с примененной котировкой

Для MVP достаточно, если часть этих данных доступна через списки, группировки и стандартные Odoo-отчеты без отдельного BI-контура.

## 12. Ограничения и редакционные решения первой версии

В первой версии:
- не вводится отдельный `metal_id` в строку материала, если его можно получить через `alloy_id`
- не вводится отдельный документ движения металла
- не ведется автоматический расчет возврата клиентского лома
- не реализуется многошаговая переоценка при выдаче заказа
- не реализуется полноценная прослеживаемость металл-партии
- процент безвозвратных потерь не участвует в формуле цены строки и резервируется для следующего этапа

Редакционное решение:
- основным пользовательским полем выбора должен быть `alloy_id`
- металл отображается как производное и аналитическое поле

## 13. Бизнес-сценарии

### 13.1. Приемка изделия

Приемщик:
- создает заказ
- выбирает сплав изделия
- вводит вес при приемке

Система:
- определяет металл через сплав
- считает эквивалент чистого металла

### 13.2. Добавление металлического материала в заказ

Пользователь:
- добавляет строку материала
- указывает продукт, вес и при необходимости корректирует сплав

Система:
- подставляет дату котировки
- находит актуальную котировку металла
- рассчитывает вес возвратных потерь по настройке продукта
- рассчитывает цену строки
- сохраняет примененную котировку

### 13.3. Изменение даты котировки в заказе

Пользователь:
- меняет `metal_rate_at` в шапке заказа

Система:
- может применить новую дату к строкам материалов, которые не имеют своего индивидуального `rate_datetime`
- пересчитывает такие строки

### 13.4. Выдача заказа

Пользователь:
- фиксирует вес при выдаче

Система:
- пересчитывает разницу веса
- пересчитывает эквивалент чистого металла на выходе

## 14. Критерии приемки

Контур считается реализованным корректно, если:
- в заказе можно указать сплав изделия и веса на входе и выходе
- система автоматически определяет металл по сплаву
- система рассчитывает `weight_delta`, `fine_weight_received`, `fine_weight_delivered`
- в заказ можно добавить строку металлического материала с отдельным сплавом
- по строке металлического материала можно задать вес и дату котировки
- система автоматически рассчитывает `weight_loss` по проценту возвратных потерь продукта
- система находит актуальную котировку по металлу и дате
- цена металлической строки рассчитывается по сплаву и весу с учетом `weight_loss`, а не по статичной цене товара
- фактически примененная котировка сохраняется в строке
- при отсутствии нужной котировки пользователь получает явную ошибку
- материалы, добавленные из операции, остаются частью единого контура материалов заказа
- данные металл-контура доступны в форме заказа и в печатной или табличной аналитике

## 15. Следующий этап после MVP

Следующей итерацией можно формализовать:
- правила списания металла со склада
- использование процента безвозвратных потерь в отдельной логике ценообразования или себестоимости
- учет клиентского лома и металла
- перепроверку котировок на этапе выдачи
- более строгие права на редактирование металл-данных после выдачи
- специализированные отчеты по металлу для руководителя и производства
